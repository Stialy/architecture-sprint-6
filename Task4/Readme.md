### 2. Требуется ли ему своё хранилище данных?

Да, как и другим сервисам. 
База будет содержать специфичные данные для сервиса и обрабатывать их разными истансами сервиса при масштабироании.
Для базы данных использую PostgreSQL.

### 5. Подумайте над API для веб-приложения в core-app

Тк от бизнеса есть требование по отображению данных для клиента - сразу, как только пришел ответ,
по требуется реализация асинхронного API

* Веб приложение формирует запрос на расчет ОСАГО, включая в него необходимые для расчет данные
  * Марка автомобиля
  * Год выпуска
  * Страховая стоимость
  * Стаж включенных у страховку водителей
* "Подписка" на получение обновлений Web приложений от core-app

### 6. Определите средство интеграции между веб-приложением и core-app. Если будете использовать средство, отличное от REST, отразите интеграцию новой стрелкой.

Предлагаю использовать WebSockets, с помощью которого установим постоянное соединение между веб приложением и core-app, которое будет отправлять данные о расчитанных страховках в реальном времени.

### 7. Применение патернов отказоустойчивости

RateLimiting использую на входящий поток от веб приложения и Систем Партнеров, это позволит ограничить поток запросов, контролировать нагрузку на систему, соблюдение SLA на интеграцию Систем Партнеров

Timeout, Retry, CircuitBreaker - на взаимодействие с Системами страховых компаний
Требований (SLA) на количество запросов к Страховым система нет, использование RateLimiting не требуется

Timeout, Retry - для внутренних взаимодействий, например, публикация сообщений на шину

### 8. Влияние на использование патернов отказоустойчивости в случае запуска нескольких экземпляров сервисов

Изменений не вижу. Взаимодействия с внешними системами от количества запушенных экземпляров сервисов не зависит.
Единственное, RateLimiting на входящий трафик будет применятся на LoadBalancer, который будет распологаться ДО экземпляров сервисов, например на NGIX или API Gateway.
